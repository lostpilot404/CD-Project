Why this was reported

Potential command injection flow detected: data introduced at line 8 (input) reaches argument 0 of system() at line 10, which rule 'command_system' classifies as a 'command' context operation. The taint engine propagated the atom(s) src:stdin@command along 7 recorded step(s): input() introduces untrusted data (source rule 'stdin') (line 8) -> 'name' is assigned a tainted value at line 8 (line 8) -> argument 0 of the call to build_command() is tainted (line 9) -> 'user_input' is a parameter of build_command() (line 3) -> build_command() returns a tainted value (line 4) -> call to build_command() propagates taint to the caller (line 9) -> 'command' is assigned a tainted value at line 9 (line 9). The flow crosses at least one function boundary, so the interprocedural summary was used. The flow rule 'command_execution' connects source 'stdin' to sink 'command_system' and lists sanitizers shell_escape, parse_to_int, validate_command; none of them removed the atoms that reached this sink. Analysis certainty: approximate. This is a static finding: exploitability was not established.

Limitations of this finding
Interprocedural reasoning is context-insensitive: parameters are summarised across all call sites, which can add flows that a single call site cannot actually create.
The flow was detected by static analysis only; the analysed program was never executed and exploitability was not established.
Remediation

Do not build a command from untrusted input. Prefer a fixed program path with arguments passed as separate values; if a shell string is unavoidable, escape the value for the command context (for example with the 'shell_escape' rule) and re-run the analysis to confirm the flow disappears.
